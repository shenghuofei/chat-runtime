# 架构设计（Architecture）

本文档描述 chat-runtime 的整体架构、数据流、上下文管理策略、Prompt Cache 优化、会话生命周期以及安全设计。

chat-runtime 是一个基于 Go 的 LLM Agent 运行时框架，采用自研的 Agent 编排层（不依赖任何三方编排框架），支持多种 LLM Provider、MCP 协议工具集成、三种上下文溢出策略、会话持久化、CLI + WebSocket 双模式，并以单一二进制（内嵌前端）方式部署。

---

## 1. 整体架构分层

chat-runtime 采用清晰的分层架构，自上而下依次为 **Transport 层 → Agent 层 → Provider / Manager / Tools 层 → Store 层**。每一层职责单一、依赖向下单向流动，便于替换和测试。

```
┌───────────────────────────────────────────────────────────┐
│                        Transport 层                         │
│      CLI (readline)          │      WebSocket (gorilla/ws)  │
│  一次性任务 / 交互式 REPL      │      Web 前端 / 远程接入       │
└──────────────┬───────────────────────────┬─────────────────┘
               │                           │
               │  统一的输入/输出事件流（stream events）
               │                           │
┌──────────────▼───────────────────────────▼─────────────────┐
│                          Agent 层                           │
│   ┌────────────┐   ┌──────────────────┐   ┌─────────────┐   │
│   │  Session   │   │  Tool Calling    │   │  Approval   │   │
│   │  会话管理   │──▶│  循环编排         │──▶│  审批流      │   │
│   └────────────┘   └──────────────────┘   └─────────────┘   │
└────────┬─────────────────┬──────────────────────┬──────────┘
         │                 │                      │
┌────────▼──────┐  ┌────────▼───────┐  ┌───────────▼──────────┐
│   Provider    │  │    Manager     │  │        Tools         │
│  多 LLM 适配   │  │   上下文管理    │  │  内置 + MCP + 自定义   │
│  统一接口      │  │ compress/      │  │  统一 Tool 接口       │
│               │  │ truncate/window│  │                      │
└───────────────┘  └────────────────┘  └──────────────────────┘
         │
┌────────▼──────────────────────────────────────────────────┐
│                          Store 层                          │
│      checkpoint（会话快照） + JSONL（增量事件日志）           │
└────────────────────────────────────────────────────────────┘
```

### 1.1 Transport 层

Transport 层负责与外部世界交互，将不同接入方式统一为标准的输入/输出事件流，屏蔽下层对具体传输协议的感知。

- **CLI（readline）**：基于 readline 的交互式 REPL，支持历史记录、多行输入与流式渲染；同时支持 `--once` 一次性任务模式，适合脚本化调用。
- **WebSocket（gorilla/websocket）**：面向 Web 前端与远程接入，通过 WebSocket 推送流式 token、工具调用事件与审批请求。前端静态资源通过 `go:embed` 内嵌进二进制，无需额外部署。

两种传输方式共享同一套事件模型（文本增量、工具调用、工具结果、审批请求、错误、结束），因此 Agent 层无需关心当前运行在 CLI 还是 Web 模式。

### 1.2 Agent 层

Agent 层是整个运行时的编排核心，为自研 Agent 编排（由 agent.Run 主循环编排），主要包含三个子模块：

- **Session（会话管理）**：维护单次会话的消息历史、上下文状态、关联的模型与工具集，负责与 Store 层交互进行持久化与恢复。
- **Tool Calling 循环**：驱动"LLM 调用 → 解析 tool_calls → 执行工具 → 回填结果 → 再次调用 LLM"的多轮循环，直到模型返回不含工具调用的终止响应。
- **Approval（审批流）**：在工具执行前插入 Human-in-the-loop 检查点，对危险操作要求用户显式确认（详见第 6 节安全设计）。

### 1.3 Provider / Manager / Tools 层

这三者是 Agent 层的三大依赖，互相解耦：

- **Provider（LLM 适配）**：通过统一接口对接 OpenAI / Claude / DeepSeek / Ollama / 火山引擎(Ark) / Gemini / Qwen 等多种 LLM，屏蔽各家 API 差异。上层只面向统一的 `ChatModel` 抽象。
- **Manager（上下文管理）**：负责在上下文超出预算时执行溢出策略（compress / truncate / window），保证请求不超过模型上下文窗口，同时尽量保留关键信息。
- **Tools（工具集）**：统一 Tool 接口，聚合三类工具来源——内置工具（命令执行、文件操作）、MCP Server 提供的远程工具、以及自定义工具。

### 1.4 Store 层

Store 层负责会话持久化，采用 **checkpoint + 增量日志** 的组合：

- **checkpoint**：会话的结构化快照，记录当前完整的消息历史与元数据，用于快速恢复。
- **JSONL 增量日志**：以追加方式记录每一个事件（消息、工具调用、结果等），提供细粒度审计与断点续写能力。

进程重启后，Agent 可从 checkpoint 加载基线状态，并按需回放增量日志，从而恢复完整上下文。

## 2. 数据流详解

一次完整的对话请求，从用户输入到最终输出，会经历如下数据流。以"用户输入 → LLM 调用 → Tool Calling 循环 → 流式输出"为主线：

```
用户输入
   │
   ▼
[Transport] 接收原始输入（CLI 行 / WS 消息）
   │
   ▼
[Session] 追加 user 消息到消息历史
   │
   ▼
[Manager] 检查上下文预算 → 必要时执行溢出策略（compress/truncate/window）
   │
   ▼
[Provider] 组装请求（system + history + tools 定义），标准化以命中 Prompt Cache
   │
   ▼
[LLM] 流式返回 delta（文本增量 / tool_calls）
   │
   ├──▶ 若为纯文本：直接经 Transport 流式输出给用户 ──▶（结束）
   │
   └──▶ 若包含 tool_calls：进入 Tool Calling 循环
             │
             ▼
        [Approval] 判断该工具是否需要审批
             │
             ├── 需审批 ──▶ 向用户发起审批请求 ──▶ 用户批准/拒绝
             │                                        │
             │                              拒绝 ─────┘（回填拒绝结果）
             │                              批准
             ▼
        [Tools] 执行工具（内置 / MCP / 自定义）
             │
             ▼
        [Session] 将 tool 结果作为 tool 消息回填历史
             │
             ▼
        回到 [Manager] → [Provider] → [LLM] 再次调用
             │
             ▼
        （循环，直到 LLM 返回不含 tool_calls 的终止响应）
   │
   ▼
[Session] 持久化本轮消息与事件到 Store
   │
   ▼
输出完成
```

### 2.1 关键说明

- **流式优先**：LLM 的输出以 delta 形式流式推送，Transport 层实时渲染，降低首字延迟（TTFB）。
- **Tool Calling 是循环而非单次**：一轮 LLM 响应可能触发多个工具调用，工具结果回填后需再次调用 LLM，直到模型不再请求工具。循环存在最大轮次上限（由上下文管理与运行时保护共同约束），防止无限循环。
- **审批发生在执行前**：只有通过审批（或被配置为自动批准）的工具才会真正执行；被拒绝的工具会以"用户拒绝"的结果回填，交由 LLM 决定后续策略。
- **持久化贯穿全程**：每一步产生的事件都会写入增量日志，关键节点更新 checkpoint。

## 3. 上下文管理三种模式

随着对话轮次增加，消息历史会不断膨胀，最终超出模型上下文窗口。Manager 层提供三种溢出策略，通过 `context_manager.mode` 配置选择。

三种模式的对比：

| 模式        | 核心思想                     | 信息保真度 | 额外成本         | 适用场景                       |
|-------------|------------------------------|------------|------------------|--------------------------------|
| compress    | 摘要压缩早期历史              | 高（有损） | 需额外 LLM 调用   | 长对话、需保留早期语义          |
| truncate    | 按轮次丢弃最早的消息          | 低         | 无                | 只关心近期上下文、追求低延迟    |
| window      | 按 token 预算维持滑动窗口      | 中         | 需精确 token 计数 | 需要精确控制上下文体积           |

### 3.1 compress（摘要压缩）

当上下文接近预算上限时，将较早的一批消息交给 LLM 生成摘要，用一条精炼的 summary 消息替换原始的多条消息，从而在保留语义的前提下大幅缩减 token。

- 相关配置：
  - `max_tokens`：触发压缩的 token 阈值。
  - `compress_ratio`：压缩目标比例（例如 0.5 表示压缩后目标降到约一半）。
- 优点：最大程度保留早期对话的关键信息与意图。
- 代价：压缩本身需要一次额外的 LLM 调用，带来延迟与费用；摘要为有损压缩，细节可能丢失。
- 建议：适合客服、长任务规划等需要"记住很久以前发生了什么"的场景。

处理示意：

```
[系统][早期消息 1..N][近期消息] ──压缩──▶ [系统][摘要(1..N)][近期消息]
```

### 3.2 truncate（截断）

按对话轮次（round）保留最近 `max_rounds` 轮，超出的最早消息被直接丢弃（system 提示词始终保留）。

- 相关配置：
  - `max_rounds`：保留的最大对话轮次数。
- 优点：实现简单、零额外成本、延迟最低。
- 代价：早期信息完全丢失，不适合需要长程记忆的任务。
- 建议：适合一问一答、上下文相关性随时间快速衰减的场景。

处理示意（max_rounds = 3）：

```
[系统][轮次1][轮次2][轮次3][轮次4][轮次5] ──截断──▶ [系统][轮次3][轮次4][轮次5]
```

### 3.3 window（token 窗口）

维护一个基于 token 预算的滑动窗口，从最新消息向前累加 token，直到达到 `max_tokens`，更早的消息被移出窗口（system 提示词始终保留）。

- 相关配置：
  - `max_tokens`：窗口的 token 上限。
- 优点：对上下文体积的控制最精确，能稳定地贴近模型窗口上限而不溢出。
- 代价：需要对每条消息进行 token 计数；与 truncate 类似，被移出窗口的信息会丢失。
- 建议：适合对 token 成本敏感、需要精确控制请求体积的生产场景。

处理示意：

```
从最新消息向前累加 token ≤ max_tokens：
[系统]      ...   [msg_k]...[msg_n]
             ▲               ▲
        （被移出窗口）     （保留在窗口内）
```

### 3.4 选择建议

- 追求信息完整、可接受额外开销 → `compress`
- 追求最低延迟、上下文短程相关 → `truncate`
- 追求精确的 token 控制 → `window`

## 4. Prompt Cache 优化策略

主流 LLM Provider（如 Claude、OpenAI、DeepSeek 等）支持 **Prompt Cache**：对相同前缀的请求内容进行缓存复用，从而降低费用并显著减少延迟。chat-runtime 在请求组装阶段做了多项优化以最大化缓存命中率。

### 4.1 稳定前缀（Stable Prefix）

Prompt Cache 通常以"最长公共前缀"为粒度命中。因此 chat-runtime 保证**越靠前的内容越稳定**：

- **system 提示词固定在最前**：system 内容在整个会话生命周期内保持不变，作为最稳定的缓存前缀。
- **工具定义（tools schema）紧随其后并排序**：将工具定义的顺序做**确定性排序**（如按工具名字典序），避免因工具注册顺序变动导致前缀变化、缓存失效。
- **历史消息按时间顺序追加**：新消息只在尾部追加，不改动已有前缀，使得每轮请求都能复用上一轮已缓存的前缀。

### 4.2 消息标准化（Normalization）

不同来源产生的消息可能存在格式差异（空白字符、字段顺序、可选字段的有无等），这些差异会破坏前缀一致性。chat-runtime 在发送前对消息做标准化：

- 统一字段序列化顺序，避免同义不同形。
- 规整多余空白与空字段。
- 保证同一逻辑内容在不同轮次序列化结果一致。

### 4.3 缓存断点（Cache Breakpoint）

对于支持显式缓存标记的 Provider（如 Claude 的 `cache_control`），chat-runtime 会在稳定前缀的末尾（system + tools 之后）设置缓存断点，使这一大块稳定内容被完整缓存。

### 4.4 上下文管理与缓存的权衡

需要注意：上下文溢出策略会**改动消息历史前缀**，从而可能使缓存失效。

- `truncate` / `window`：移除早期消息会改变前缀，触发一次缓存重建。
- `compress`：用摘要替换早期消息，同样改变前缀。

因此实践中应在"控制上下文体积"与"保持缓存命中"之间取得平衡，例如不要过于频繁地触发压缩/截断。

## 5. 会话生命周期

一个会话（Session）从创建到销毁，经历如下阶段：

```
创建(Create) ──▶ 就绪(Ready) ──▶ 运行(Running) ──▶ 空闲(Idle) ──▶ 关闭(Closed)
     │                              │  ▲                │
     │                              ▼  │                │
     │                        Tool Calling 循环          │
     │                                                  │
   加载配置                                          持久化 + 释放资源
   （model/tools/system）                          （flush 增量日志）
```

1. **创建（Create）**：根据 `chats` 配置解析出关联的 model、工具集、system 提示词（含 `@file:` 引用与 Go 模板变量渲染），初始化 Session 与 Store 句柄。若指定了历史会话 ID，则从 Store 加载 checkpoint 并回放增量日志。

2. **就绪（Ready）**：Session 已加载完毕，消息历史与工具就位，等待用户输入。

3. **运行（Running）**：接收用户输入后进入运行态，执行"数据流详解"（第 2 节）描述的完整流程，可能包含多轮 Tool Calling 循环。运行期间实时产生事件并写入增量日志。

4. **空闲（Idle）**：一轮请求结束后回到空闲态，等待下一次输入。空闲期间会将本轮的 checkpoint 落盘。

5. **关闭（Closed）**：会话结束（用户退出、连接断开或显式关闭）时，flush 剩余的增量日志、更新最终 checkpoint、释放 Provider / MCP 连接等资源。

### 5.1 恢复（Resume）

得益于 Store 层的 checkpoint + 增量日志，进程重启或连接重连后可恢复会话：

1. 从 checkpoint 载入基线消息历史与元数据。
2. 回放 checkpoint 之后的增量日志，补齐未落盘的最新状态。
3. 恢复到 Ready 态，继续接受输入。

## 6. 安全设计

chat-runtime 面向"让 LLM 执行真实操作（命令、文件、集群）"的场景，因此内置了 Human-in-the-loop 的安全机制，核心是**命令执行白名单**与**审批机制**。

### 6.1 审批机制（Human-in-the-loop）

任何工具在真正执行前，都会经过 Approval 环节判定是否需要用户确认：

- **需审批的工具**：在执行前暂停，向用户（CLI 提示 / Web 审批弹窗）发起审批请求，展示将要执行的具体操作（如完整命令、目标路径、参数）。用户可选择：
  - **批准**：继续执行工具。
  - **拒绝**：跳过执行，以"用户拒绝"结果回填给 LLM，由模型决定后续动作。
- **自动批准的工具**：通过配置声明为自动批准（见 6.3），无需人工介入直接执行，适合只读或低风险操作。

审批粒度可精确到单个工具，兼顾安全与效率。

### 6.2 命令执行白名单

内置的命令执行工具（command）是风险最高的能力，因此提供白名单约束：

- 只有命中白名单的命令/子命令才允许执行，未命中的一律拒绝或强制转入审批。
- 白名单可结合审批机制使用：白名单内的低风险命令自动放行，白名单外的命令需人工审批。
- 建议在生产环境中：默认拒绝一切，显式列出被允许的命令，遵循最小权限原则。

### 6.3 auto_approve 配置

MCP Server 与工具可通过 `auto_approve` 声明审批策略，支持三种粒度：

- **全部自动批准**：`auto_approve: true` —— 该 Server 下所有工具均自动执行（仅建议用于可信、只读或受控环境）。
- **指定工具自动批准**：`auto_approve: [tool_a, tool_b]` —— 仅列表内的工具自动执行，其余需审批。
- **全部需审批**：`auto_approve: false` 或不配置 —— 所有工具都需人工确认（最安全的默认策略）。

### 6.4 纵深防御建议

- 生产环境优先使用 `truncate`/`window` 之外的最小权限原则，工具默认需审批。
- 命令执行工具启用白名单，禁用危险命令（如 `rm -rf`、`dd`、凭证读取等）。
- MCP Server 的 `auto_approve: true` 仅用于确实可信的只读服务。
- Web 模式下为 WebSocket / HTTP 接口启用 `server.basic_auth`，避免未授权访问触发工具执行。
- 敏感信息（API Key、KUBECONFIG 等）通过环境变量注入，避免硬编码进配置文件并入库。
